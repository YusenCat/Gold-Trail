# 4.0 公网联机调研与实施规划

调研日期：2026-10-09。3.5.0已发布；本文是4.0开发基线，不表示公网服务已经上线。

## 常见体验与实现方式

| 方式 | 官方实例或依据 | 接入方式 | 对黄金邮道的判断 |
| --- | --- | --- | --- |
| 浏览器大厅与桌号 | [Board Game Arena FAQ](https://en.boardgamearena.com/faq)描述选择桌、加入、等待玩家、开始游戏 | 打开网站，进入房间 | 适合自动规则和2／4人对战；保留选位、准备流程 |
| 浏览器共享房间 | [PlayingCards.io快速指南](https://playingcards.io/docs/overview)描述创建房间、分享房间码及同步操作 | 打开房间，朋友凭码进入 | 借鉴简单邀请流程；该平台规则由玩家执行，黄金邮道继续由服务器裁定 |
| 客户端主机与点对点 | [Tabletop Simulator技术说明](https://kb.tabletopsimulator.com/getting-started/technical-info/)明确列出Steam P2P、公私房间和好友连接 | 安装客户端，通过平台入房 | 适合已有平台生态；不适合本项目“朋友打开网页就能玩”的目标 |
| 浏览器WebRTC点对点 | [MDN连接说明](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Connectivity)说明信令、ICE及TURN中继 | 房间信令后建立设备连接 | 仍需服务器协助；主机离线、秘密状态和跨设备恢复要额外设计，首版成本更高 |
| 中心服务器运行规则 | [boardgame.io多人文档](https://github.com/boardgameio/boardgame.io/blob/main/docs/documentation/multiplayer.md)描述由master计算状态并广播，客户端提交动作 | HTTPS站点＋服务器房间 | 与现有架构一致，优先复用现有代码；不迁移规则引擎 |

推荐结论属于结合现有代码的工程判断：单实例Node.js 24中心服务器＋HTTPS＋持久磁盘最省开发和接入步骤。现有HTTP动作与SSE状态推送适合回合制，不为公网接入单独重写WebSocket传输。邀请链接携带入房信息，不能授予其他人的角色权限。

## 部署选项

1. **托管Node服务＋持久磁盘**：优先用于初次上线。平台提供公网域名与TLS，可配置启动命令和健康检查，见[Render Web Services](https://render.com/docs/web-services)。当前JSON恢复文件必须放在挂载目录；[Render磁盘说明](https://render.com/docs/disks)指出默认文件系统临时、持久磁盘可跨重启和部署保留。磁盘方案先使用一个实例，不宣称多实例共享状态。
2. **已有云服务器＋Docker＋Caddy**：适合已有资源或希望自行选择地区。反向代理负责HTTPS；[Caddy文档](https://caddyserver.com/docs/automatic-https)说明域名与自动证书。Node只开放容器内部端口，恢复文件使用独立持久卷。
3. **Cloudflare Durable Objects**：其[官方示例](https://developers.cloudflare.com/durable-objects/examples/websocket-hibernation-server/)提供WebSocket及休眠能力，可作为以后按房间扩展的选项。当前Node文件存储与服务入口需要适配，首版不选择。

免费临时文件系统不能满足房间恢复：[Render免费服务说明](https://render.com/docs/free)明确说明空闲休眠及重启丢失本地文件、不支持持久磁盘。首版不把这样的部署标为正式可恢复服务。无需预先锁定供应商或购买资源；最终地区、预算、域名待部署资源确定后验收。

## 目标体验

访问大厅 → 创建2／4人房间 → 复制邀请链接 → 朋友打开、输入昵称 → 选位准备 → 开始对局。

默认私密房间不出现在公共列表；公开房间显示人数、玩法和可加入状态。房间码仍可手工输入。初版无需账号、排行榜、聊天或支付。

## 按顺序实施

| 阶段 | 开发内容 | 通过条件 |
| --- | --- | --- |
| A：公网服务边界 | 明确public／LAN运行模式；固定公网origin与域名白名单；HTTPS来源校验；public模式关闭所有本地对局、教学、存档和主机统计入口；Secure玩家Cookie；健康检查与部署配置 | 反向代理来自127.0.0.1仍不能访问本地API；允许配置域名；错误Host／Origin及伪造转发头不能改变信任边界；旧局域网行为通过回归 |
| B：创建与分享 | 复用2／4人选位、准备和服务器裁定；公网大厅文案；私密邀请令牌与公开房间列表；邀请令牌独立于席位凭证；生成同一HTTPS站点的链接 | 两个独立浏览器身份可通过分享链接加入；私密房不列出；列表不泄露手牌、玩家凭证或未公开状态；所有动作仍校验角色与版本 |
| C：换设备与恢复 | 一次性换设备凭证，由已登录玩家生成、短期有效、兑换后撤销旧凭证；原有Cookie同设备自动回房；恢复文件持久化与旧档兼容；命令去重；断线暂停、全员在线后继续 | 新设备回到同一角色；旧设备不能再落子；过期／重复兑换失败；稽查每个阶段均可断线和服务重启恢复；同一动作不重复扣资源 |
| D：运行与容量 | 空闲房间回收及存档保留政策；按玩家／来源限制创建与加入；并发房间队列独立；代理不缓冲SSE；日志不记录身份令牌；部署与备份恢复说明 | 多房间互不覆盖；公开入口容量可控；重启和升级恢复；损坏单档不影响其他房间；完成持久卷恢复演练 |
| E：手机与公网验收 | 320／390竖屏、844横屏，2／4人完整对局；Wi-Fi与蜂窝网络切换、前后台、刷新、慢网重试、邀请分享、换设备 | 两个不同网络的真实设备完成创建→分享→入房→结算；4人完整对局、秘密信息隔离与全部恢复场景通过后发布4.0.0 |

每阶段先实现和回归，再用视觉操作验证玩家流程。接口测试只验证权限、持久化和协议；试玩不调用引擎或隐藏状态替玩家行动。保持3.5的横竖屏布局，不加入开发说明。

## 已确认的现状与缺口

现有RoomService已有2／4人席位权限、独立房间队列、SSE过滤、命令收据去重、断线暂停和服务重启恢复，可以复用。

现入口拒绝非IP域名，Origin固定为HTTP；本机权限基于连接地址，反向代理可能令公网请求呈现为loopback。这些必须在阶段A显式修复，不能直接将3.5局域网服务暴露到公网。现有浏览器Cookie不支持跨设备取回同一席位，阶段C增加明确恢复流程。

尚未确定可用部署账号、主机、域名及预算。可先完成全部可部署代码与本机代理验收；正式上线与不同网络验收须有真实部署资源，不用localhost结果代替公网结论。

## 实施记录

2026-10-09：阶段A的服务边界已实现，固定HTTPS origin、Host／Origin校验、public模式禁用本地接口、Secure Cookie、代理限流来源识别与健康检查通过测试。已提供Docker＋Caddy模板和部署说明；开发机无Docker，容器构建及证书实测待完成。

阶段B已实现默认私密房间、独立256位邀请令牌、公开空位列表和前端入口。邀请令牌置于链接fragment，不进入请求URL或Referer；加入时提交给同站点服务。既有成员可凭原Cookie重连；邀请令牌不能作为席位凭证。公开列表不含玩家身份、邀请令牌、手牌或局面。13项部署、HTTP、房间及恢复检查通过。公网浏览器和不同网络视觉验收仍待部署资源，当前不宣称4.0发布完成。

阶段C已实现五分钟一次性换机链接；兑换后保持玩家、席位和局面，撤销原凭证与旧SSE连接，排队请求再次检查凭证。权威凭证注册表独立持久化，旧房间恢复文件不能在重启后复活已撤销身份；注册表缺失或损坏时停止恢复。补测并发兑换、旧链接作废、过期、跨房间同身份、磁盘失败不消费链接和重启撤销。

使用页面完成本机换设备流程：原设备127.0.0.1建立房间并选走私者，使用localhost的独立Cookie身份打开换机链接，接回同一房主和席位，原页面显示已退出。检查390像素竖屏并修复房间标题与在线提示对比不足。此项是本机界面验证，不代替真实不同网络设备验收。

阶段D已加入全员离线候场24小时／完局7天归档，完整记录保留，未完成对局不自动归档；失败入房身份回收，入房请求期间身份有保留锁，真实成员及其他房间身份不误删。归档失败保留房间；维护与重启保持未完成局面。创建／加入的排队请求同样再次检查凭证。持久磁盘、SSE代理配置、备份与容量说明已补齐，容器和真实公网验收仍待部署环境。

阶段E已完成本机双人三十轮视觉试玩，结算22比24；第13轮服务重启保留四名角色位置、资源和原决策，重连后继续完成。修复联机控制在桌面及横屏位置过低、文字对比不足的问题，检查390×844与844×390布局。详见[试玩记录](PLAYTEST_4_0.md)。真实公网与不同网络设备验收仍待部署资源。

四人视觉对局已通过页面完成四席准备、开局和全部30轮，逐页核对结算均为25比19；对局中的换设备保留同一角色和原决策，并完成后续移动。修复角色切换或换局时行动面板旧滚动位置导致标题裁切，以及队友手牌只读提示不明确。浏览器控制在第三、第四个地址曾调用较慢，后恢复顺畅并继续原局完成。复查桌面与390×844、844×390结算画面。

补充Render原生Node Blueprint：单实例、持久磁盘、健康检查、构建时公网回归与手工部署。启动器使用平台固定HTTPS URL或明确配置的自定义域名，始终启用public模式；本机启动回归验证无效配置拒绝启动及本地权限隔离。模板通过官方Schema校验。实际托管服务和不同网络验收仍需要部署账号或已有主机。

补齐阶段C的稽查恢复协议验收：2人和4人分别在响应、分箱、问话、选箱时模拟断线并重启，验证原决策与资源保留、命令去重、操作权交接和秘密箱量过滤。该检查不替代公网实机恢复验收。
